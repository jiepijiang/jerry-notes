# Agent Note: App 先用 uni-app 跑通，之后用 AI 重构到 Flutter

## 问题

App 这一端要同时满足两个诉求，而它们在短期内是冲突的：

- **要快**：业务逻辑（尤其是和嵌入式设备通信那部分）需要尽早拿到真机上验证，
  在浏览器里模拟串口 / BLE 的行为和真机差太远。
- **要长期可维护**：uni-app 的多端抽象在复杂交互上会漏水，
  一旦要做原生能力（后台常驻、蓝牙、串口），补丁会越打越厚。

## 决策

**分两步走，先不追求一步到位：**

1. **第一阶段用 uni-app 把流程跑通。** 一套代码同时出 H5 和小程序，
   业务逻辑、状态管理、接口层都在这阶段定型。
2. **第二阶段用 AI 辅助重构到 Flutter。** 有了第一阶段验证过的业务逻辑，
   重写的风险从「需求对不对」降到「语法对不对」—— 而这恰好是 AI 最擅长的部分。

关键前提是**第一阶段就要为重构留路**：业务逻辑尽量写成纯函数 / 纯数据变换，
UI 层薄、少用平台特有 API，把「和原生打交道」的部分收敛到少数几个模块里。

## 曾考虑的替代方案

**直接用 Flutter 起步**——搁置。Flutter 的 Dart 生态对我来说是全新的，
从零学 + 从零写，第一阶段的时间会被拉长很多，而这一阶段真正需要的是**快速验证业务逻辑**。
另外小程序端 Flutter 支持不成熟，等于放弃一个端。

**直接用 React Native**——否决。虽然 React 我熟，但 RN 在小程序端同样没有好方案，
而且和现有技术栈（Vue 系）的心智模型割裂，反而增加切换成本。

**一套 uni-app 用到底，不重构**——否决。这等于赌「永远不会遇到复杂原生需求」，
而嵌入式设备方向恰恰是原生需求最密集的场景。

## 后果

- 短期拿到速度：uni-app 一套代码覆盖 H5 + 小程序 + App。
- 中期拿到质量：Flutter 阶段可以针对真机做原生能力，不再受抽象层限制。
- **代价是「两次实现」**。所以第一阶段的代码要克制：不追求架构漂亮，
  但必须把业务逻辑和 UI 分开 —— 否则第二阶段等于重做需求。
- 待验证：AI 辅助重构的实际效果（能省多少时间、哪些部分仍要手写）。
  这条现在还只是计划，跑完第一阶段才谈得上评估。
