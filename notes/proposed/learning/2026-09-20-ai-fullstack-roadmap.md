# Agent Note: AI 学习路线 —— 以能跑起来的项目为主线

## 问题

想往 AI 方向走（目标是全栈），但学习路径有两条截然不同的走法：

- **理论优先**：先补线性代数、概率、深度学习原理，再动手
- **项目优先**：先搭能跑的东西，遇到不懂的再回去补

理论优先的问题是**反馈周期太长** —— 学三个月还没产出任何东西，
很难判断自己是不是走在对的方向上，也容易中途放弃。

## 决策

**以「能跑起来的项目」为主线，理论按需补。**

具体的推进顺序：

1. **先把本地模型跑起来**（Ollama）。目标是搞清楚「一次推理到底发生了什么」——
   模型加载、上下文窗口、token 计费、流式输出，这些是后面一切的地基。
2. **再做一次完整的 RAG**：切分文档 → 向量化 → 检索 → 拼进 prompt → 生成。
   这一步会把「embedding 是什么」「为什么要 rerank」这类概念**逼出来**。
3. **然后做 Agent**：工具调用、多轮状态、错误恢复。
   这一步是「全栈」里「栈」的部分 —— 前后端 + 模型 + 工具编排。
4. **最后回到理论**，补那些在做项目时反复撞到但没深究的点。

技术栈上先用 **LangChain + Ollama** 起步（本地可跑、零成本试错），
不急着上云服务 —— 本地能跑通再谈成本优化。

## 曾考虑的替代方案

**先系统学完机器学习课程**——搁置。不是否决，是排序问题：
理论在「知道要解决什么问题」之后学，效率高得多。现在硬啃容易变成背公式。

**直接上云 API（OpenAI / Claude）起步**——搁置。
成本是小事，**关键是本地模型能让我看到「内部状态」**：
显存占用、上下文长度限制、量化等级的影响。
云 API 把这些都藏起来了，对理解原理不利。

**从微调入手**——否决。微调是「有了明确任务和评估标准之后」的优化手段，
现在连任务都没定，微调等于盲目调参。

**只做调用层，不碰原理**——否决。那样天花板是「会调 API」，
遇到效果不好时无法判断该改 prompt、换模型还是改检索 —— 而这正是 AI 全栈的核心能力。

## 后果

- 每一步都有可展示的产出（本地推理 → RAG → Agent），
  正好可以做成主页上的项目卡片，学习成果本身就是作品集。
- 代价：**理论是欠账**。前期一定会写出「能跑但不知道为什么能跑」的代码。
  这个欠账必须在第 4 步还上，否则会停在「会调 API」的水平。
- 待验证：这条路线是否真的比理论优先更快见效。
  现在只是计划，跑完前三步才谈得上评估 —— 到那时回来更新这条记录。
