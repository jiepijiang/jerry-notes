# Agent Note: 导航站先不上 Supabase，只做可替换的数据层

## 问题

导航站的参考实现是 React + Supabase：书签存云端，多设备同步，
还有用户体系。看起来很完整。

但把它放到我的场景里对一遍：

- **用户只有我自己一个**，不需要多用户和权限体系
- **数据量很小**（几百条书签），localStorage 完全放得下
- 上 Supabase 意味着：注册账号、配 RLS 策略、处理网络失败、引入一个 SDK 依赖，
  以及——**离线时打不开自己的书签**

## 决策

**先不上云。** 把数据层抽成一个可替换的适配器，当前实现是 localStorage：

```js
// src/data/storage.js —— 全部返回 Promise，换后端只改这一个文件
export const storage = {
  read(key) {},
  write(key, value) {},
  remove(key) {},
  readAll() {},
  writeAll(map) {},
}
```

业务键统一加 `jt:` 前缀，避免和同域下的其它应用撞车。

**所有方法都返回 Promise**，这一点是刻意的 ——
localStorage 是同步的，很容易写出同步的调用代码，
那样以后换异步后端就要改遍所有调用点。现在多写几个 `await`，
换来的是「换后端只改一个文件」。
（这个适配器服务的是[导航站](2026-09-19-nav-site-bookmarks.md)）

## 曾考虑的替代方案

**直接上 Supabase**——搁置（不是否决）。它确实是参考实现的选择，
而且多设备同步是真实需求。但现在上是**为了一个还不存在的需求付出确定的成本**。
等「我真的需要在手机上改书签」这件事发生，再上不迟 —— 那时适配器已经就位，
换过去只改一个文件。

**用 GitHub Gist 当存储**——否决。要处理 token、要处理冲突、
每次读写都要走一次网络，比 localStorage 还慢，而且离线照样打不开。

**用 IndexedDB**——否决。几百条书签用不上 IndexedDB 的容量和索引能力，
而它的 API 复杂度（事务、游标）明显高于收益。

**干脆不做数据层抽象，直接用 localStorage**——否决。
这是最容易的写法，也是唯一会让「以后换后端」变成大工程的写法。

## 后果

- 现在：打开即用、离线可用、零依赖、零成本。
- 未来：真需要同步时，只需替换 `storage.js` 里的五个方法。
- 代价：**没有多设备同步**。换台电脑要手动导出导入。
  这是当前唯一的真实损失，而且现在还不是痛点。
- 顺带一条经验：**参考实现的技术选型不等于我的技术选型**。
  对着参考站抄之前，先问「它解决的哪个问题我有」。
