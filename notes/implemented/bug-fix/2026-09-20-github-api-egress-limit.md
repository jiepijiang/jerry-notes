# Agent Note: 第三方公开 API 改到构建期取数，别在浏览器里直连

## 问题

首页「最近在做什么」原本在组件 `onMounted` 里直接 `fetch` GitHub 公开 API。
本地开发一切正常，**线上访客看到的却是一句「暂时取不到 GitHub 数据」**。

排查：Playwright 打线上，抓到 `403 https://api.github.com/users/jiepijiang/repos?...`。
但本地直连 `curl` 同一个地址是 **200，还剩 60 次额度**。

差别在**出口 IP**：

| 环境 | 出口 IP | 结果 |
| --- | --- | --- |
| 开发机直连 | 独立 | 200，额度够用 |
| 浏览器走代理 | **所有访客共享** | 403 |

未登录的 `api.github.com` 限流是 **60 次/小时/出口 IP**，共享出口很容易被别人用光。
**这个 bug 只有真实访客会踩到，本地开发机永远复现不出来。**

## 决策

**改成构建期生成一份静态 JSON，运行时对 GitHub 的请求数降为 0。**

```js
// scripts/gen-recent.mjs
const res = await fetch(url, { headers: { ...(token ? { authorization: `Bearer ${token}` } : {}) } })
```

几个刻意的设计：

1. **拉取失败时绝不覆盖已有文件**（`existsSync(OUT)` 直接 `exit 0`）。
   CI 里一次网络抖动不该把线上数据刷成空白 —— 宁可继续用昨天的数据。
2. **存绝对时间戳**（`pushedAt`），「1 小时前」这类相对时间由前端实时算。
   否则数据放一天，「3 小时前」就变成错的。
3. **CI 里注入 `secrets.GITHUB_TOKEN`**（额度 5000/小时，不会限流），
   本地没 token 也能跑（未登录够用）。
4. 工作流挂一个**每日定时**，不推代码也会刷新数据。

## 曾考虑的替代方案

**加缓存 / 重试**——否决。限流是按 IP 的，重试只是把 403 重复几遍。
缓存只能救「已经成功过一次」的访客。

**换一个第三方代理接口**（如 `gh-proxy`、`raw.githack`）——否决。
把可用性押在另一个不受控的免费服务上，问题只是换了个地方发生。

**做成 GitHub Action 定时提交数据文件**——否决。会产生大量无意义的 commit 污染历史。
CI 里构建前跑一次脚本、产物随部署走，干净得多。

**直接去掉这一块**——否决。它是首页唯一「活着」的部分（会随时间变化），
值得留。

## 后果

- 运行时零外部依赖，页面永远不会因为第三方挂掉而空一块。
- 数据最多滞后一天（定时任务兜底），对「最近在做什么」这个语义完全够用。
- 代价：**数据不是实时的**。刚 push 完不会立刻出现在首页，要等下一次部署或定时任务。
- 顺带一条通用教训：**「本地全绿」对这类问题毫无证明力**。
  验收标准应该写成「运行时对第三方域名的请求数 = 0」，在 Playwright 里断言，
  而不是「我看了一眼页面是好的」。
