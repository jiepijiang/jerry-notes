# Agent Note: 深色底上的图标可读性由填充面积决定，不是颜色亮度

## 问题

技能树重做时，36 个品牌图标放在深色方块（`#242938`）上。
有些图标的品牌色本身就偏深（深蓝、深紫），压在深色底上糊成一团，需要提亮成白色。

第一版按「相对亮度 < 0.5 → 白色」处理，结果 **23/36 全变白了**，
整面墙的花色全没了，比糊掉更难看。

换成 WCAG 对比度重新卡，结论更矛盾：
**npm 的红对比度只有 2.87，比 MySQL 的 3.10 还低**，
但 npm 是整块实心方块，读起来毫无问题；MySQL 却是细描边海豚加小字，糊得看不清。

## 决策

**通用规则用「相对亮度 < 0.22」**（只捞纯黑那一档），
再对「亮度过关但因为是细描边 / 深色实心块而糊掉」的**逐个列白名单**：

```js
const toReadable = (hex) => {
  const [r, g, b] = [0, 2, 4].map((i) => parseInt(hex.slice(i, i + 2), 16))
  const lum = (0.2126 * r + 0.7152 * g + 0.0722 * b) / 255
  return lum < 0.22 ? '#ffffff' : `#${hex}`
}

/** 亮度过关但细描边 / 深色实心块而糊掉的，逐个列白名单 */
const FORCE_WHITE = new Set(['siMysql', 'siVitepress'])
```

**关键动作是把 SVG 放大 4 倍逐块看。** 这两个白名单条目不是算出来的，是看出来的 ——
只看颜色值和对比度数字，永远发现不了。

（这面墙本身是脚本生成的，见[重复性资产用生成器产出](2026-09-20-skill-tree-generator.md)）

## 曾考虑的替代方案

**统一全部转白**——否决。最省事，但整面墙变成一片白，
技能树就失去了「一眼看出用了什么技术」的作用，而那正是它的全部价值。

**给每个图标加白色描边 / 底衬**——否决。等于给 36 个图标各加一层装饰，
视觉噪音比问题本身大，而且破坏了 simple-icons 的原始形状。

**按对比度阈值自动判断**——否决。npm（2.87）比 MySQL（3.10）对比度更低却更清楚，
这个反例说明「对比度」这个指标根本没抓住问题的本质。

## 后果

- 整面墙保持品牌色，只有真正糊掉的少数几个变白，观感统一。
- 白名单是**显式的、可审计的**：以后加图标如果发现糊，就往 `FORCE_WHITE` 里加一条，
  不会影响已有图标。
- 代价：白名单是手工维护的，换图标集时要重新肉眼过一遍。
  但这本来就是「看」出来的结论，没法自动化 —— 硬要自动化只会得到一个错的规则。
- 可复用的判据：**决定深色底上图标可读性的，是填充面积，不是颜色。**
