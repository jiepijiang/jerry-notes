# Agent Note: 重复性资产用生成器产出，数据与代码分离

## 问题

技能树是一面 36 个方块的 SVG 图标墙。第一版是直接写 SVG 的 ——
加一个图标要手算坐标、复制粘贴 `<g>` 块、改 `transform` 里的偏移。
改一次错一次，而且没法验证「36 个方块的位置是不是等距」。

另外，这面墙的内容会变（技术栈在变），手写意味着**每次变更都是一次手工重排**。

## 决策

**写一个生成器，把数据抽成 JSON。**

```
scripts/skill-icons.json     ← 图标清单（顺序即排列顺序）
scripts/gen-skill-tree.mjs   ← 生成器，读 JSON 输出 SVG
```

三条约束：

1. **生成器零依赖。** 为了重新生成一面图标墙在项目里挂个几十 MB 的图标包不值得。
   图标数据（`title` / `hex` / `path`）导出成 JSON 提交进仓库，
   脚本读它即可 —— 顺带把图标集**版本化固定住**，不会因为上游更新而意外变样。
2. **版式参数逐项照抄原件。** 方块 256、圆角 60、底色 `#242938`、列距 300、
   同样的 `viewBox` 和外层 `width/height`。这样渲染尺寸天然不变，
   换内容不会顶动页面总高。
3. **生成器只做确定性变换。** 同样的输入必须产出同样的输出，
   否则每次构建都产生 diff，没法用 git 判断「到底改了什么」。
   （配色怎么定的，见[深色底上的图标可读性](2026-09-19-icon-fill-area.md)）

## 曾考虑的替代方案

**继续手写 SVG**——否决。已经证明会出错，而且改一次的成本随时间线性增长。

**直接引用图标包的 CDN**——否决。运行时依赖一个外部服务，
和「导航站不用第三方 favicon 服务」是同一个道理。
另外图标包会变，站点视觉会跟着上游漂移。

**用现成的图标墙组件库**——否决。要引入依赖、要适配它的版式，
而我要的只是「36 个方块等距排列」这一件事。

**生成器直接 `import` 图标包**——否决。会让 `node_modules` 变成
「重新生成图标墙」的前置条件，而这是个一年动两次的操作。
数据分离之后，重新生成只需要 Node 本身。

## 后果

- 换 36 个图标只需改 JSON 再跑一行命令，版式零影响
  （实测换完整套图标后页面总高仍是 1115，关键元素盒模型逐项一致）。
- 构建产物从 102 KB 瘦到 47.7 KB（生成时顺手做了路径压缩）。
- 代价：**仓库里同时存在「数据」和「产物」两份**。
  要写清楚「不要手改 SVG」（README 里单独一节），否则下一个人会去改产物，
  然后下次生成时被覆盖掉。
- 一条可复用的判据：**当一个资产是「同一结构 × N 个数据项」时，就该上生成器。**
  反之，一次性的布局不要生成器 —— 那只是把 HTML 换成更难读的代码。
